Have you ever tried using a user journey map to plan your documentation and realized it doesn't quite fit?

I recently built a documentation website from scratch. It was the first time I had taken on such a project, and I was intimidated by it. I resolved to use a user journey map to help me build a list of articles that I could write and publish on the website. So, I started with a standard UX journey mapping framework. These types of maps focus on touchpoints, interactions, frictions, and the users' feelings. The disconnect hit me when I asked myself: "What are the touchpoints in documentation?"

Technical writers deal with a small fraction of the product. We don't craft interactions, but learning paths. Our users ask questions and search for answers to solve real problems. That's when I realized: we need a different journey map.

## A different kind of journey

Documentation is a critical part of the product experience, especially for developers. And sometimes it is the first way developers interact with your product. Developers come to your documentation looking for answers to questions:

- Does this product solve my problem?
- Is it compatible with my current tools?
- How do I get started?
- What are the best practices?
- Why is this not working?

Thus, when done right, documentation can help:

- Evaluate a product
- Adopt and learn how to use it
- Unstick themselves when something breaks

In other words, documentation can contribute to customer satisfaction, confidence, and advocacy.

But here's the catch: traditional journey maps cover all product interactions. These maps include touchpoints with sales, marketing, and customer support. But for us, the experience only happens within the documentation website.

Why I built a user journey map for documentation
User problems are business problems. If a user can't find the information they need, they might not adopt the product, or worse, they might churn. If you satisfy your readers' needs, you will satisfy your business's goals.

When I couldn't find a journey mapping framework that focused on content, I decided to build my own. I based it on user questions and learning paths, not touchpoints or interactions. Let me now tell you how I built my documentation journey map.

## My process for building a documentation journey map

These are the steps I followed to create a documentation-specific user journey map.

I used Fabrizio Ferri-Benedetti's Seven-action documentation model as the backbone for the journey stages. Fabrizio's model outlines seven key things users try to do with documentation:

Appraise: Understand what the product is and whether it's worth trying.
Understand: Learn key concepts and mental models.
Explore: Try out the product in a safe, low-stakes way.
Practice: Perform day-to-day tasks and workflows.
Remember: Recall syntax, parameters, or settings.
Develop: Extend or integrate the product into custom workflows.
Troubleshoot: Diagnose and fix problems

### Step 1: Value proposition
I connected users' pain points to the solutions the product offers. This helped me understand how documentation could bridge the gap between problems and solutions.

### Step 2: Product questions
I gathered questions users typically ask about the product. I also included some questions from the Developer journey map by Caroline Lewko and James Parton. Then I organized these questions according to the seven journey stages.

### Step 4: Content plan
I created a list of articles to write based on the users' questions identified in earlier steps. Using this approach ensures that every article has a purpose.

The result: A content plan that maps user questions to articles across each journey stage. This ensures your documentation supports real user goals and drives business outcomes.

## How this map improves documentation
Using this model helped me create documentation that answers key questions:

- What is this persona trying to achieve?
- What questions do they have at each stage?
- What emotions are they experiencing?
- What kind of content would help them most?
- Are there any gaps in the docs?

It's a practical, content-focused, and repeatable approach. By applying this journey map to your documentation planning process, you will:

- Create docs that have a clear purpose and help your readers.
- Align your documentation with the business's goals.
- At the end of the day, effective content achieves a goal. When you understand what your users want to do, you can write documentation that gets them there with clarity, confidence, and efficiency.

## Where to go from here
When I started building a documentation site from scratch, I felt overwhelmed. I didn't know where to begin or what to prioritize. Using this documentation journey map grounded me. It gave me a practical way to understand my users, plan meaningful content, and move forward with confidence.

If you're facing a blank page or an endless backlog, try starting with your users' journey. Ask what they're trying to do and what questions block their progress. This mindset shift transforms documentation from a reactive checklist into a proactive, strategic tool.

You only need a commitment to empathy, clarity, and purpose.
