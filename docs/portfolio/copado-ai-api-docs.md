## Summary

AI Context Hub's API documentation was a single static article with partial endpoint coverage and a link to a raw OpenAPI file auto-generated by FastAPI. The file listed routes outside the supported public API, had almost no descriptions, and gave developers no way to try a request. 
On my own initiative, I replaced it with a curated 24-endpoint OpenAPI specification, an API overview, and an interactive console in the documentation portal. I used AI to audit the generated spec and map its resources. 
I used AI to audit the generated spec and map its resources. I then checked the spec by calling the documented endpoints with curl and Postman, and engineering reviewed and signed it off before publication.

- Stack: OpenAPI (JSON), ClickHelp, Postman, curl, Claude Code

## Problem

The static article covered only the minimum needed for a basic call, and its code examples were inconsistent: some could be copied, others couldn't. The linked generated spec added six more problems:

- Scope: It listed every route in the service, including routes that weren't part of the supported public API.
- Naming: Operation IDs were verbose and unstandardized, such as `list_workspaces_organizations__organization_id__workspaces_get`.
- Descriptions: Endpoint descriptions were incomplete or missing, and parameters had no context.
- Authentication: It listed five security schemes without saying which one customers should use.
- Servers: Copado runs on multiple regional servers, and none were documented.
- Examples: There was no concrete reference for a successful response.

## Approach

### 1. Audit the generated spec with AI

I gave the generated spec to Claude Code and asked it to audit the spec for the issues a customer would hit. Its findings became the problem list above. I treated them as a checklist to verify against the file, not as a source of truth.

### 2. Decide what is public

I derived the public scope from the product itself. I listed the actions a user can take in the AI Context Hub UI and kept only the endpoints that back one of them. Routes with no matching UI action stayed out. I took the resulting 24 endpoints to engineering, who validated the list and clarified several parameters and response fields.

### 3. Map the resources

Following a strategy Tom Johnson describes on [I'd Rather Be Writing](https://idratherbewriting.com/ai/prompt-eng-api-qrgs.html), I used AI to build a reference diagram of the API's resources and endpoints, grouped by resource. I put it in the API overview so developers can see what they can do with the API.

### 4. Author the specification

I wrote a new OpenAPI specification in JSON for the 24 endpoints:

- User-facing descriptions
- Standardized operation IDs
- Tags by resource
- The regional servers
- Reusable parameter and schema components
- Realistic response examples
- Documented 401, 403, 404, and 422 responses

### 5. Validate against the real API

I called the documented endpoints with curl and Postman to check request formats and responses against the spec before anything was published. I ran these checks by hand.

### 6. Ship the console and the overview

ClickHelp supports OpenAPI natively, but the live console failed on CORS. I worked with engineering and infrastructure to allow incoming calls from ClickHelp. In parallel, I wrote the API overview: how to authenticate, the reference diagram, core concepts, resource identifiers, and a quickstart.

### Collaboration

I led the work and wrote all content. Engineers validated the public scope, reviewed the reference and overview, and helped me resolve the CORS issue.

## Results

- A curated, customer-facing scope of 24 endpoints, signed off by engineering.
- A hand-authored specification with standardized operation IDs, tags, regional servers, response examples, and documented 401, 403, 404, and 422 responses.
- A live API console in the documentation portal, so developers can test requests where they read about them.
- An API overview with authentication guidance, a reference diagram, and a quickstart.
- A specification owned by the documentation team instead of an unmaintained generated file.

## Decisions and trade-offs

- UI parity as the scope rule: It gave me a defensible way to decide what was public. The cost is that it can leave out API-only capabilities customers might need, so I'd revisit the rule with Product.
- AI as auditor, not authority: AI sped up the audit and the reference diagram, but scope came from the product and engineering, and accuracy came from review and live calls.
- A hand-authored spec over a generated one: Customers get far better quality. The cost is drift, because a manual copy can fall behind the service.
